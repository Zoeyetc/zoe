# Z.land Music Box — Experience Composition v0.1

## 1. Purpose

This document defines how the already-validated Z.land Music Box systems should
be composed into one audience-facing spatial experience.

It does NOT redefine:

- AudioWorld
- Musical Evidence
- actor musical responsibilities
- actor-local simulation
- PhysicsWorld
- current musical mappings

Those systems are already established.

This document owns:

- spatial composition
- Park Map structure
- overview / focus behavior
- attention hierarchy
- region emphasis
- actor placement
- visitor orientation
- cross-world readability
- composition across desktop / tablet / mobile
- final experience transition away from the current vertical development page

The core objective is:

> Let the visitor perceive one song operating one shared physical park while
> still preserving precise local musical evidence.

---

## 2. Experience identity

The intended experience is not:

```text
a dashboard
```

and not:

```text
a vertical collection of ride demos
```

and not:

```text
a conventional theme-park illustration
```

The intended experience is:

```text
a persistent shared park
+
a spatial score
+
a physical musical world
```

The visitor should be able to perceive:

```text
one song
→ many simultaneous musical truths
→ multiple actor interpretations
→ one shared physical environment
```

---

## 3. Spatial Score principle

A useful internal concept is:

```text
Spatial Score
```

Traditional notation primarily organizes:

```text
time
×
pitch
```

Z.land organizes musical evidence through:

```text
time
×
space
×
mechanical behavior
×
physical causality
```

The Park Map is therefore not only navigation.

It is the spatial organization of a musical performance.

However:

```text
Park Map
≠
Musical Evidence
```

The map organizes attention and geography.

The actors expose the music.

---

## 4. Musical Evidence remains exact

Experience Composition must never falsify Musical Evidence.

Examples:

```text
Carousel note carrier
→ real melody note
```

```text
FerrisWheel active cabins
→ real chord-tone membership
```

```text
BumperCars impulse
→ real percussion event
```

```text
DropTower release
→ real explicit drop event
```

Experience Composition may alter:

- scale
- camera attention
- contrast
- line weight
- region emphasis
- opacity
- surrounding detail

It must not alter:

- note identity
- chord membership
- event occurrence
- structural event truth
- actor musical responsibility

---

## 5. Park Map is not a domain dashboard

Do not organize the final map as isolated music-theory panels.

Avoid:

```text
MELODY ZONE
HARMONY ZONE
RHYTHM ZONE
STRUCTURE ZONE
```

Avoid:

```text
domain available
→ district light ON
```

Prefer physical geography organized around:

- rides
- paths
- tracks
- movement corridors
- force fields
- shared open space
- landmarks
- interaction proximity
- visitor orientation

The musical-domain meaning should be inferred through actor behavior.

---

## 6. Persistent overview

The final experience should allow the visitor to perceive multiple actors
within one persistent world.

The user should not need to scroll between:

```text
Carousel
FerrisWheel
PirateShip
BumperCars
DropTower
RollerCoaster
```

while the same song continues.

A persistent overview should make it possible to perceive simultaneous musical
dimensions.

The visitor does not need equal detail for every actor at all times.

The world should remain coherent even when attention shifts.

---

## 7. Overview and Focus are separate scales

The experience likely requires two perceptual scales:

```text
OVERVIEW
```

and:

```text
FOCUS
```

### Overview

Purpose:

- understand whole-park state
- see simultaneous activity
- perceive cross-actor relationships
- observe major musical structure
- maintain spatial orientation

At overview scale:

- all primary actors should remain identifiable
- exact micro-evidence may be simplified visually but must remain truthful
- no actor should become an unrelated symbolic replacement

### Focus

Purpose:

- inspect precise local Musical Evidence
- understand actor mechanics
- observe note / chord / physical response detail

Focus must not become:

```text
a separate disconnected detail page
```

Prefer:

```text
same park
+
local emphasis / zoom / framing
```

so surrounding world context remains perceptible where practical.

---

## 8. Focus must not stop the world

When one actor enters Focus:

- AudioClock continues normally unless the user pauses
- other actors continue simulation
- PhysicsWorld continues
- Musical Evidence elsewhere remains valid
- shared physical causality remains active

Focus changes presentation.

It does not pause the world by default.

---

## 9. Attention hierarchy

Actors may occupy one of four experience roles:

```text
Primary
Secondary
Ambient
Resting
```

### Primary

Carries the dominant current narrative / musical event.

Examples:

- Carousel during the first melody reveal
- DropTower during pre-drop hold
- RollerCoaster during major phrase release

### Secondary

Musically meaningful and visible, but not dominant.

### Ambient

Maintains continuity and musical context without demanding attention.

### Resting

Physically present but musically inactive or settled.

These roles affect presentation only.

They must not alter Musical Evidence.

---

## 10. Evidence survives hierarchy

If FerrisWheel is Ambient:

```text
real chord tones
→ still remain represented
```

If Carousel is Primary:

```text
only real melody notes
→ remain represented
```

Wrong:

```text
Primary
→ invent extra musical carriers
```

Wrong:

```text
Ambient
→ hide actual Musical Evidence
```

Correct:

```text
same evidence
+
different presentation emphasis
```

---

## 11. Region emphasis

Actor districts / spatial regions may receive subtle emphasis.

Region emphasis exists only to help the visitor locate activity.

Possible tools:

- line weight
- local contrast
- subtle fill
- density
- localized illumination
- map texture
- motion trace
- spatial halo
- camera framing

Do not use region emphasis as the primary Musical Evidence display.

Example:

Correct:

```text
G4 note
→ exact Carousel carrier responds

Carousel area
→ receives subtle attention support
```

Wrong:

```text
melody active
→ whole Carousel district lights up
```

with no exact note evidence.

---

## 12. Global visual restraint

The final Park Map should avoid default theme-park illustration language.

Avoid automatically adding:

- cartoon grass
- decorative trees
- castles
- mascots
- crowds
- colorful amusement-park scenery
- nostalgic fairground decoration
- decorative roads with no physical function

Prefer:

- schematic
- mechanical
- diagrammatic
- abstract
- spatial
- low-noise
- media-neutral
- line-based
- restrained monochrome or limited-color systems

Color may be used later.

It is not required for spatial comprehension.

---

## 13. Actor geography

Actor placement should serve three goals simultaneously:

1. spatial readability
2. musical-role legibility
3. physical interaction opportunity

Do not place actors only for visual symmetry.

Placement should consider:

- RollerCoaster route
- wake interaction
- Free Body movement
- PhysicsWorld proximity
- overview visibility
- future focus transitions
- Gate orientation
- major vertical landmarks

---

## 14. Carousel spatial role

Carousel represents local melodic detail.

Spatial characteristics:

- compact
- readable from overview
- accessible to Focus
- enough visual resolution for precise carrier hits
- not hidden behind large structures

It may occupy a central or near-central readable zone.

Its location is not locked.

---

## 15. FerrisWheel spatial role

FerrisWheel is a large visual landmark.

It represents sustained harmony and simultaneous chord-tone evidence.

Spatial characteristics:

- large silhouette
- readable cabin distribution
- enough separation to distinguish active harmonic carriers
- slower visual rhythm than Carousel
- useful as an orientation landmark

It may occupy an edge / upper region / major skyline position.

Exact placement is not locked.

---

## 16. PirateShip spatial role

PirateShip represents groove and continuous swing.

Spatial characteristics:

- requires lateral breathing room
- pendulum arc must remain readable
- should not visually collide with unrelated major structures
- may sit near an open shared field

Its oscillation should be readable at overview scale.

---

## 17. BumperCars spatial role

BumperCars represents percussion and collision.

Spatial characteristics:

- defined local arena
- enough space for body/body collision
- visible relation to nearby PhysicsWorld participants
- potential proximity to Anchored Content / Free Bodies

The arena should feel spatially contained without becoming an isolated UI card.

---

## 18. DropTower spatial role

DropTower represents build / tension / major drop.

Spatial characteristics:

- strong vertical landmark
- clear top / bottom
- visible hold state
- readable from overview
- useful as an attention anchor during structural tension

The DropTower may help define the vertical scale of the park.

---

## 19. RollerCoaster spatial role

RollerCoaster should not be contained inside one small district.

It is a major spatial connector.

Its route may:

- cross multiple areas
- pass near other actors
- establish directional flow
- create physical wake interactions
- visually connect distant parts of the park

This supports its musical role:

```text
Phrase / Energy / Tension / Release
```

The route itself may become one of the main compositional lines of the Park Map.

---

## 20. Free Bodies spatial role

Free Bodies / Orb do not require a dedicated district.

They belong to:

```text
global atmosphere
```

They may:

- travel across actor regions
- respond to RollerCoaster wake
- respond to BumperCars impacts
- occupy shared fields
- interact with future colliders
- cross ordinary content zones

Their mobility helps make the park feel like one continuous physical world.

---

## 21. Anchored Content spatial role

Ordinary content may exist inside the world.

Examples:

- title
- labels
- navigation
- project card
- text
- image

Content should retain authored layout while receiving temporary PhysicsWorld
response.

Content placement should not block important actor mechanics.

Content may also provide useful spatial reference points for physical causality.

---

## 22. Gate / Ticket Booth

Gate / Ticket Booth should exist near the spatial edge of the park.

Conceptually:

```text
outside
↓
Gate
↓
inside Z.land
```

This supports:

```text
Bring a Song
→ Ticket
→ Enter
→ Music starts
→ Park performs
```

Do not place the primary entrance UI in the middle of the park unless the final
experience deliberately requires it.

The entrance metaphor remains replaceable.

---

## 23. Park boundary

The first Park Map prototype should define a clear but abstract spatial
boundary.

It may use:

- irregular land shape
- bounded mechanical field
- schematic frame
- contour
- open planar territory

Do not overdesign terrain.

The boundary's job is to establish:

```text
inside Z.land
vs
outside
```

and give actor geography a shared frame.

---

## 24. Paths

Paths may be introduced only when they serve:

- visitor orientation
- spatial grouping
- actor relation
- route continuity
- visual rhythm

Do not add decorative roads merely because amusement-park maps usually contain
roads.

Paths should be functional in composition.

---

## 25. RollerCoaster track vs map paths

Do not confuse:

```text
RollerCoaster physical track
```

with:

```text
visitor / map path
```

The RollerCoaster track is actor geometry and simulation infrastructure.

Map paths are experience-composition elements.

They may cross visually but must remain conceptually separate.

---

## 26. Precise evidence readability

The Park Map must preserve exact local Musical Evidence.

This is especially important for:

```text
Carousel
FerrisWheel
```

At full overview, exact micro-detail may become visually small.

Therefore the composition should support:

```text
overview
↔
focus
```

without replacing exact evidence with generic status symbols.

Do not simplify:

```text
C / E / G
```

into:

```text
HARMONY ACTIVE
```

as the only visible state.

---

## 27. Overview evidence strategy

At overview scale, evidence may use restrained cues such as:

- active carrier fill
- line weight
- small localized pulse
- precise position
- bounded luminance / contrast change
- motion envelope

The representation may be simplified.

The identity must remain truthful.

---

## 28. Focus evidence strategy

At focus scale, actors may expose richer evidence.

Examples:

### Carousel

- carrier identity
- note name optionally
- pitch height
- onset / duration
- local note expression

### FerrisWheel

- exact active chord-tone carriers
- optional chord label
- root / pitch-class information
- cabin swing

### BumperCars

- recent percussion event
- collision origin
- physical consequence

Focus may expose more information.

It must not invent new musical truth.

---

## 29. User interaction model

Initial interaction should remain minimal.

Potential interactions:

- click/tap actor to Focus
- click/tap empty park area to return to Overview
- play / pause / seek through ControlSurface
- optional actor info overlay
- optional debug mode

Do not introduce:

- drag-to-rearrange park
- complex editor interactions
- ride customization
- map-building tools

during the first Experience Composition milestone.

---

## 30. Camera model

The first spatial prototype should avoid cinematic complexity.

Prefer:

- mostly stable overview
- modest focus zoom / reframe
- gentle camera interpolation
- preserved orientation

Avoid:

- rapid cuts
- aggressive orbiting
- music-video camera choreography
- camera motion that hides cross-actor causality

The camera should help the visitor read the park.

It should not become the main spectacle.

---

## 31. Camera does not create physics

Camera movement must never create fictitious physical motion.

Do not interpret:

- pan
- zoom
- viewport movement
- responsive reframe

as actor velocity.

PhysicsWorld remains in canonical world coordinates.

Rendering / camera transforms are downstream.

---

## 32. Desktop strategy

Desktop should prioritize:

```text
persistent overview
```

Possible behavior:

- full park visible
- actor detail readable enough for broad evidence
- Focus uses local zoom / emphasis
- Debug UI remains outside final experience mode
- minimal page scrolling

Do not simply preserve the current vertical actor-card stack.

---

## 33. Tablet strategy

Tablet may use:

- slightly tighter park framing
- fewer peripheral labels
- selective simplification of map decoration
- local Focus reframe

The same shared-world topology should remain recognizable.

---

## 34. Mobile strategy

Mobile must not degrade into:

```text
six vertical actor cards
```

merely because screen width is smaller.

Possible mobile strategies include:

- responsive Park Map viewport
- pan / zoom
- guided focus framing
- simplified overview
- stronger actor focus with surrounding context
- minimap / spatial locator if necessary

The exact mobile strategy is not locked.

What is locked:

> The final mobile experience should preserve the idea of one shared world.

---

## 35. No horizontal-scroll-as-final-layout rule

Do not solve small screens by placing all actor districts in a giant horizontal
strip unless a later explicit design decision chooses that behavior.

The shared world should remain spatially meaningful.

---

## 36. Current vertical development page

The existing vertical page remains available during Experience Composition
development.

Do not delete it immediately.

It is useful as:

```text
development mode
```

for:

- actor QA
- debugging
- raw state inspection
- regression checks

The Park Map should initially be added as a separate experience composition
mode or clearly isolated new composition layer.

Do not destroy the development workbench until the new composition is stable.

---

## 37. Park Map must compose existing actors

This is critical.

Do not implement simplified fake ride animations inside one giant ParkMap
component.

Correct:

```text
existing Carousel
existing FerrisWheel
existing PirateShip
existing BumperCars
existing DropTower
existing RollerCoaster
existing Free Bodies
existing PhysicsWorld
↓
Experience Composition
```

Wrong:

```text
ParkMap.tsx
→ manually redraw and animate fake simplified versions of every actor
```

The Park Map owns composition.

It does not own actor simulation.

---

## 38. Renderer reuse vs composition renderer

Actor simulation remains canonical.

A new Park Map composition may require:

- new renderer adapters
- shared SVG composition
- shared Canvas renderer
- spatial wrappers
- viewport transforms

This is allowed.

But new renderers must read existing actor state.

Do not fork actor simulations.

---

## 39. One live actor instance rule

There must be one authoritative live simulation instance per actor.

Do not create:

```text
one Carousel for dev card
+
one Carousel for Park Map
```

running simultaneously from separate simulation states.

Both development and final renderers should read the same underlying actor
truth where architecture allows.

If mutually exclusive modes are used, state ownership must still remain
unambiguous.

---

## 40. Park Map coordinate space

Experience Composition must use the existing PhysicsWorld canonical coordinate
space as the shared spatial basis where practical.

Do not invent:

```text
Park Map coordinates
```

that are unrelated to PhysicsWorld coordinates if actors must physically
interact.

Preferred:

```text
Park Map world position
=
PhysicsWorld world position
```

or:

```text
explicit reversible adapter
```

The relationship must be documented.

---

## 41. Actor layout anchors

Actors need authored spatial anchors inside the Park Map.

These anchors define:

- district position
- local renderer bounds
- spatial relation to other actors
- PhysicsWorld adapter reference

Actor simulation may remain local.

The composition layer determines where the actor's local system lives in the
shared park.

---

## 42. Local actor space vs park world space

Maintain explicit separation:

```text
actor-local simulation space
→ actor spatial adapter
→ Park / PhysicsWorld space
```

Examples:

```text
FerrisWheel local SVG geometry
→ placed at FerrisWheel park anchor
```

```text
BumperCars local arena
→ placed at BumperCars park region
```

```text
RollerCoaster route
→ already spans larger world region
```

Do not hide these transformations inside visual CSS hacks.

---

## 43. Cross-actor proximity

Actor placement should make validated and future physical interactions
meaningful.

Examples:

```text
RollerCoaster route near Free Body field
→ wake interaction
```

```text
BumperCars arena near Anchored Content
→ collision impact response
```

Spatial composition should not claim physical proximity where canonical world
coordinates say objects are far apart.

---

## 44. Activity density

The park must not become uniformly busy.

A full musical arrangement does not mean every actor should visually dominate.

Use:

```text
Primary
Secondary
Ambient
Resting
```

to maintain perceptual hierarchy.

Free Bodies should not fill every empty area merely because space exists.

Silence and empty space are valid composition elements.

---

## 45. Color strategy

Color is not required for Milestone 8A.

Initial prototype may use:

- black
- white
- grays
- one restrained accent
- one limited monochrome family

Do not use rainbow actor colors simply to differentiate domains.

Musical identity should come primarily from behavior and spatial organization.

---

## 46. Line-weight strategy

In a monochrome system, line weight may communicate:

- actor importance
- active focus
- spatial hierarchy
- map structure
- mechanical depth

But it must not encode false musical facts.

---

## 48. Educational / inspection mode

- note names
- pitch
- chord label
- chord tones
- beat phase
- swing
- build
- phrase progress

This mode can strengthen the transcription / score feeling.

The main experience should still work behaviorally.

## 49. Time remains AudioClock-owned

The final Park Map does not own musical time.

Do not make:

```text
scroll
→ song progress
```

the default behavior.

AudioClock remains authoritative.

The visitor may navigate spatially while musical time continues independently.

---

## 50. Focus and seek are different

Do not confuse:

```text
focus actor
```

with:

```text
seek music
```

Focusing FerrisWheel should not change song time.

Seeking song time should not automatically change spatial focus unless a later
experience rule explicitly requires it.

---

## 51. Map state is not simulation truth

Park Map state may include:

- focus target
- overview zoom
- viewport transform
- region emphasis
- camera interpolation

It must not own:

- actor velocity
- note identity
- chord membership
- collision state
- PhysicsWorld force
- musical time

## 57. Success criteria

The Park Map direction succeeds when the visitor can perceive:

```text
one world
```

rather than:

```text
six demos
```

and:

```text
multiple simultaneous musical truths
```

rather than:

```text
six domain status indicators
```

while:

```text
exact notes / chord tones / events
```

remain truthful.

---

## 58. Experience composition invariant

When making a composition decision, ask:

1. Does this preserve exact Musical Evidence?
2. Does this preserve actor simulation ownership?
3. Does this preserve PhysicsWorld spatial causality?
4. Does this help the visitor understand one shared world?
5. Does this reduce or increase dashboard-like behavior?
6. Does this preserve overview context?
7. Does this still allow detailed musical evidence to be inspected?
8. Is this presentation, or is it accidentally changing system truth?

The intended experience remains:

```text
one song
→ one shared park
→ many simultaneous musical truths
→ precise local musical evidence
→ real shared physical consequences
→ a spatial score that can be watched and explored
```

## 59. Milestone 8C annotation composition

Live annotations are a presentation-only sibling of actor rendering:

```text
AudioWorld / actor state / selected PhysicsWorld diagnostics
→ pure annotation projection
→ canonical actor anchor
→ deterministic Park layout
→ leader line + compact fields
```

Annotation observes system truth. Annotation never owns system truth. It cannot
write AudioWorld, actor simulation, PhysicsWorld, AttentionState, TrackMap, or
ControlSurface state.

Overview keeps one small annotation per major musical actor. Primary and
Secondary roles show the normal compact field set; Ambient and Resting roles use
less detail without rewriting exact evidence. Manual Focus expands only the
selected actor while using the same canonical anchor and Focus viewport
transform. DebugConsole remains the complete developer surface.

Facilities do not need continuous physical motion to appear alive. At a bounded
presentation update rate, changing evidence and measured physical values provide
informational activity without inventing actor motion.
